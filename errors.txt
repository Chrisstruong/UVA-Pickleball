The main slowdown is Supabase latency amplified by sequential database queries—not the Presence popup.
Measured locally:

Cold events query	5.99s
Cold registrations query	10.78s, returned 504
Warm events query	0.72s
Warm registrations query	0.61s


The payloads were tiny, so data volume is not the cause. Supabase appears cold or temporarily resource-constrained, and the page compounds this through a request waterfall.
For signed-in users, [page.tsx (line 60)](/Users/_o_chrisstruong_o_/Projects/uva-pickleball/src/app/events/page.tsx:60) can perform these sequentially:
1. Authenticate the user.
2. Fetch their profile.
3. Fetch events.
4. Fetch all registrations.
5. Fetch attendee profiles.
6. Fetch the current user’s registrations.
Because each await blocks the next query, six 600–700 ms warm requests can still take several seconds. When Supabase is cold, it becomes dramatically worse.
Additional findings:
- The Navbar makes another user/profile request after hydration, adding network activity but not blocking the initial HTML.
- Attendee names are fetched for every event before anyone opens “View Attendees.”
- All registration rows are downloaded so counts can be calculated in JavaScript.
- Event images may delay visual completion, but they do not explain the 21-second server response.
- Presence starts after hydration, so it is not responsible for the initial delay.
- Development-mode route compilation may add extra first-navigation latency.
The strongest fix would be to parallelize independent queries, lazy-load attendee names only when the modal opens, and combine counts/status into a database query or RPC. A /events/loading.tsx skeleton would also make navigation feel immediate while data loads. No code was changed during this diagnosis.

Request-waterfall improvement
Assuming each database stage takes approximately 600–700ms:
Before: 6 × 600–700ms = 3.6–4.2 seconds
After:  2 × 600–700ms = 1.2–1.4 seconds
Saved:                       2.4–2.8 seconds
That is a theoretical 66.7% reduction and 3× speedup in staged database waiting.
This is an architectural improvement: concurrency changes the total latency from approximately the sum of every request to the maximum latency within each parallel stage. It remains beneficial even when individual Supabase requests fluctuate.
Query and reliability improvements
The signed-in initial path changed from approximately six calls to four:
- Authentication and events still occur, but concurrently.
- Profile and registrations still occur, but concurrently.
- The attendee-profile request is deferred until the modal opens.
- The separate current-user registration request was eliminated.
- Attendee loading failures are isolated to the modal and now have a retry state.
The old registrations request took 10.78 seconds and returned a 504. The optimization does not guarantee Supabase will never return another 504, but:
- There are fewer initial requests that can fail.
- Slow independent calls overlap instead of accumulating.
- Attendee-profile failures cannot delay the initial page.
- The loading skeleton reaches the browser before the final data finishes.
- One delayed request no longer makes the navigation appear completely frozen.
No specific failure-rate reduction can be claimed without longer-term production monitoring.
